Governed Agent Sandbox

An AI agent runs in a sandbox on behalf of a KYC analyst. It holds no secrets, reaches every system through one gateway, and gets a fresh 5-minute credential for each call, delegated from the analyst and checked by IBM Verify.

Deployment

The ask. A KYC analyst signs in with Microsoft Entra ID and asks an agent to work a financial-crime ticket. The agent runs in a sandbox, acts only on the analyst's behalf, and must finish a small multi-step task without holding a single credential.

  1. Read Jira ticket FINCRIME-2417 (an Entra user reaching a non-Entra SaaS)
  2. Pull runbook KYC-RR-07 from GitLab
  3. Spawn a read-only subagent to gather evidence from Databricks and the directory
  4. Write the new customer risk rating to Databricks, gated on human approval

How authority flows. The analyst's Entra ID token never reaches a bank system. The gateway exchanges it at IBM Verify (RFC 8693) for a short-lived token that names both the analyst (sub) and the agent (act), and carries exactly what may be done (RFC 9396 authorization_details). Each hop can only narrow authority, never widen it. Vault turns an approved token into a 5-minute credential for the downstream system and revokes it after use. Token contents below are illustrative and abridged.

    

      

        
1Analyst signs in (Entra ID)

        
The sandbox receives this as a bearer only. It is useless against Jira, GitLab or Databricks on its own.


{
  "iss": "https://login.microsoftonline.com/<tenant-id>/v2.0",
  "aud": "api://bank-agent-sts",
  "upn": "k.analyst@bank.example",
  "amr": ["pwd", "mfa"],
  "exp": "+60 min"
}

      

      

        
2Gateway exchanges it at IBM Verify

        
The agent proves its own registered identity (actor) alongside the analyst's (subject). Verify checks the Agent Registry and access policy before issuing anything.


POST https://<tenant>.verify.ibm.com/…/token
grant_type=urn:ietf:params:oauth:grant-type:token-exchange
subject_token=<Entra ID token: k.analyst>
actor_token=<agent-kyc-parent assertion>
authorization_details=[{
  "type": "mcp_tool",
  "tool": "jira.read_issue",
  "locations": ["FINCRIME"] }]

{
  "sub": "k.analyst@bank.example",
  "act": { "sub": "agent-kyc-parent" },
  "authorization_details": [{
    "type": "mcp_tool",
    "tool": "jira.read_issue",
    "locations": ["FINCRIME"] }],
  "jti": "a41e…",
  "exp": "+5 min"
}

      

      

        
4Subagent token (downscoped)

        
The subagent authenticates to Vault with a SPIFFE SVID. Its token nests the full chain in act and allows read only. A write request fails at the exchange, so Vault never mints a write credential.


{
  "sub": "k.analyst@bank.example",
  "act": {
    "sub": "spiffe://bank.example/sandbox/kyc-evidence",
    "act": { "sub": "agent-kyc-parent" } },
  "authorization_details": [
    { "type": "databricks", "actions": ["read"],
      "locations": ["kyc.customer_risk_rating"] },
    { "type": "scim", "actions": ["read"],
      "locations": ["Users/k.analyst"] } ],
  "exp": "+5 min"
}

      

      

        
5Write token after human approval

        
Issued only after the analyst approves the step-up. Scoped to one table, one customer, one ticket.


{
  "sub": "k.analyst@bank.example",
  "act": { "sub": "agent-kyc-parent" },
  "acr": "step-up-approved",
  "authorization_details": [{
    "type": "databricks", "actions": ["write"],
    "locations": ["kyc.customer_risk_rating"],
    "identifier": "CUST-20418",
    "ticket": "FINCRIME-2417" }],
  "jti": "c93b…",
  "exp": "+5 min"
}

      

      

        
6Vault lease for the downstream call

        
Vault checks the token's RAR before minting. The credential lives in the gateway, is used once, and is revoked. The agent never sees it.


{
  "lease_id": "database/creds/kyc_writer/…",
  "lease_duration": 300,
  "renewable": false,
  "bound_to_jti": "c93b…",
  "revoked_after_use": true
}

      

    

  


  
  

    
Who owns the rules, and how they change. Agent policy is treated like any other production change at a bank: written as code, reviewed by two people, tested, deployed by a pipeline, and evidenced for audit. IBM Verify holds identity and delegation policy (token exchange, RAR, step-up). OPA (or Authorino on OpenShift) holds tool registration and egress grants. This automation is an art-of-the-possible pattern, not a supported IBM product feature.

    

      
01
Author
Policy as code in GitLab: Verify access policies, Rego for OPA, the MCP allow-list and egress hosts.

      
02
Review
Merge request with two approvals: IAM engineering and security architecture. Production changes carry a change ticket.

      
03
Test
opa test plus replay of recorded decisions, so a new rule can't silently open a path.

      
04
Deploy
Pipeline updates the Verify policy through its API and publishes the OPA bundle. Gateways reload.

      
05
Enforce
Every tool call is decided against the new policy. Unlisted tools stay invisible to agents.

      
06
Evidence
Change record plus CAEP decision events go to SIEM and GRC for audit and quarterly attestation.

OPA: egress grant (Rego)


package agent.egress

import rego.v1

default allow := false

allow if {
  input.agent.status == "active"
  startswith(input.request.url, "https://")
  input.request.host in data.egress.hosts[input.agent.id]
}

      

      

        
OPA: MCP registration (Rego)


package agent.tools

import rego.v1

default listed := false

listed if {
  input.tool.server in data.mcp.registered
  input.tool.name in data.mcp.tools[input.tool.server]
}

      

    

  


  
What this is. A teaching model of a sandboxed, identity-governed agent in a bank, adapted from IBM's NVIDIA OpenShell agent identity demo. The bank, analyst, customer, ticket and data are fictional, and the requests and tokens are illustrative. The pattern uses IBM Verify, HashiCorp Vault, an MCP gateway and OPA; confirm current product capabilities with IBM before a client session. This page is an independent illustration, not IBM software.
